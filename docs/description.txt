На схеме common_arch.png видно, что модуль управления лицензиями тесно связан с:

Сервисом лицензирования (привязка устройства, лимиты)

Модулем подписи (закрытый ключ, keystore) – для ЭЦП тикета

Админ-сервисом сигнатур (загрузка, публикация, отзыв) + S3 API для хранения сигнатур

Сервисом обновлений (манифест, версии баз) – но это больше относится к обновлению антивирусных баз, а не к лицензиям.

В предыдущем ответе я уже предложил таблицы, операции и классы Ticket/TicketResponse. Теперь дополню их в соответствии с вашей схемой:


Сервис лицензирования – отвечает за CRUD лицензий, активацию, проверку, продление. Он взаимодействует с БД и модулем подписи.

Модуль подписи – хранит закрытый ключ (например, в том же keystore.p12 или отдельном) и генерирует/проверяет ЭЦП для Ticket.

Админ-сервис сигнатур – позволяет администратору загружать новые публичные ключи (для верификации на клиенте) и отзывать скомпрометированные. В рамках учебного проекта можно упростить: хранить один фиксированный ключ в application.properties.

S3 API – используется для раздачи файлов сигнатур (например, публичного сертификата) или манифестов обновлений. Это выходит за рамки простого лицензирования, но если требуется, можем реализовать presigned‑URL для скачивания публичного ключа.
